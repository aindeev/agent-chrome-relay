Fewer round trips, checked steps

The approach behind chrome-relay do. Alexey Indeev, October 2026.

Chrome Relay lets coding agents (Claude Code, Codex, Cursor, Paseo) use your own Chrome, signed in as you, in background tabs. It was already fast: about 0.15 s per command. Agents still felt slow in the browser, and not always reliable. This page explains why, what chrome-relay do changes, and which decision models it uses and why.

The browser isn't the slow part

We measured both ends.

WhatTime
One agent-browser command through the relay (agent-browser's own headless Chrome: 13–15 ms)15–20 ms
One page script round trip through the relay and the extension~1 ms
Filling a 7-field form with a script, reading the page before every step77 ms total
Gap between two actions of a real agent (median; 4,742 actions in 181 sessions on one Mac)2.8 s
Same, 90th percentile17 s

97% of the agents' time in a session went into gaps longer than a second: the agent reading the page, thinking and choosing one click. The driving itself is about 10 ms a step. One more number: 8% of clicks were repeated at the same spot within 15 seconds, because the first one didn't take and the agent had to look again.

So the way to make agents faster in a browser is not a faster browser. It's fewer model round trips, and steps that check themselves so the agent doesn't have to.

The approach: say the goal once

chrome-relay do "Invite the new teammate as an admin" --url https://app.example.com/team/invite \
  --profile you@company.com --data "Email=ada@example.com" --data "Role=Admin" --until "text:Invitation sent"

The agent states the goal, gives the values it already knows, and says how to tell it's done. Chrome Relay then carries it out in the agent's tab. For each step, it uses the cheapest thing that works:

  1. A flow that worked before. When a run ends with its --until check met, its steps are saved for that site (element roles and labels, and which data key went where, never the values). The same kind of goal on that site replays at browser speed with the new data: no model at all.
  2. The agent's data. A --data key that names a field ("Email" finds "E-mail address") fills it, picks the dropdown option or ticks the box. No model. Values can be 1Password references, which the relay types without the agent or any model seeing them.
  3. A fast decision model for the rest: it chooses the next operation and target from a shortlist of the page's controls, and which of the agent's values goes into a field. It can't invent text, selectors or code.
  4. Hand back. Whatever it isn't sure of goes back to the agent with what was done, the page it's on, and what it was choosing between: low confidence, a field with no value, a consequential click the goal doesn't name (delete, send, pay, deploy, authorize, …), a covered button, going in circles, leaving the site. "Done" only counts when --until holds.

Steps that check themselves

Before every action the relay checks that the element is still the one the decision was about, that it's enabled, on screen and not covered by something else (open shadow roots included). After the action it waits for the page to settle, by watching the DOM rather than polling, and reads back what changed. The click or the typing goes through the same path as the agent's own commands, so the audit trail and 1Password handling apply unchanged.

Choosing the decision model

The idea of a small, fast "System 1" model choosing the next browser action came from browser-use/jev-ultrafast, which drives Google Flights with TypeSafe's Jev in about 7 seconds. Jev doesn't generate text: it returns a probability for each allowed answer to typed questions. Cloudflare's Clef models answer the same request format, and several small open models do too. We compared them on the job chrome-relay do gives them.

Latency is measured from a MacBook (M4 Max) over the public APIs, not model time in a datacenter: Cloudflare quotes 39 ms and 209 ms for the Clef models on its own GPUs. The request format and rules were written for Jev, which may favour it. Local models ran in llama.cpp on the Mac's GPU, except Laya, which ran in PyTorch. Haiku was measured on the shortlisted requests (15 elements) that chrome-relay do sends; the others on the full ones.

What we took from it

  • Jev is the fast default: as accurate as the cheap general models on real pages, at a sixth of the latency. It needs a TypeSafe key, and the page text of agent tabs goes to TypeSafe, so it's opt-in (chrome-relay decider jev).
  • Without a key, Haiku through the person's own Claude Code is just as accurate, slower, and needs nothing new. It only works as one long-running process: starting claude -p for each decision costs 4–8 s.
  • Small local models aren't ready to choose browser steps on their own. Under 1B they score 9–30%, and 3B is usable but costs about a second of GPU per step. Laya's own model card says it is "a fast base to specialise, not a zero-shot decision engine". Fine-tuning one on the steps agents actually take is a future option.
  • Shortlisting the page is nearly free. Sending the 15 elements most related to the goal, instead of all of them, kept the right answer in 100% of live steps and 87% of Mind2Web steps. It cut the request by more than half, and cost Jev 2 points and Flash-Lite 2–3 on Mind2Web, nothing on live pages.
  • Most steps don't need a model. Filling from the agent's data and replaying saved flows covers forms, sign-ins and repeated admin work without one.

In practice

Step by step, the agents we measured took a median of about 3 seconds per action, before counting the clicks they had to repeat.

Limits

  • The page reader covers HTML and ARIA controls and open shadow roots. It doesn't yet look inside iframes or closed shadow roots, and canvas apps (such as Google Docs) are out of reach.
  • A decision model can be wrong. That's why confidence is gated, consequential clicks need the goal to name them, and "done" needs --until.
  • Page text is untrusted. The model only picks among the page's own controls and the agent's own values, and the run stays on the site it started on.

Step by step, without agent-browser

For the steps do hands back, Chrome Relay now has its own commands (chrome-relay open, snapshot, click, fill, get text, screenshot, close and the rest), built on the same page scripts as do: every action checks its control first and says what changed. We only made them the default once they were as good as agent-browser, measured head to head through the same relay:

Whatagent-browserchrome-relay
Test pages where the action really happened (23)2123
open a page (real Chrome, background tab, local page)42–54 ms49–69 ms
snapshot16–22 ms15–20 ms

agent-browser missed a <div> used as a button and a link that is only an image. Getting the speed took four things: naming the caller from the kernel over a Unix socket instead of lsof (0.3 ms instead of ~170 ms, for every command); filling a field through focus and a selection, as Playwright does; reporting an action at once and waiting for the page before the next step instead, usually while the agent thinks; and polling a loading page every 10 ms. agent-browser still works through the relay for what it has and these don't: network recording, traces and video, page diffs and downloads.
